前端面试题与参考答案 ​

用法：先记住每题的结论，再结合自己做过的项目补充细节。涉及项目经历的回答是表达模板，请替换成真实经历。代码按现代浏览器和 TypeScript/Vue 3 场景书写。

一、基础语法：JavaScript、TypeScript、HTML 与 CSS ​

JavaScript ES6+ ​

1. 箭头函数和普通函数的区别，this 指向有什么不同？ ​

箭头函数语法更短，没有自己的 this、arguments、prototype，也不能作为构造函数使用。它的 this 在定义时从外层作用域词法捕获，不会随调用方式改变；普通函数的 this 由调用方式决定，作为对象方法调用时通常指向该对象，使用 new 调用时指向新实例。需要动态 this、构造实例或访问 arguments 时用普通函数；回调中希望沿用外层 this 时常用箭头函数。箭头函数不能通过 call、apply、bind 改变 this。

2. let、const、var 的区别？什么是变量提升和暂时性死区？ ​

var 是函数作用域，可重复声明，声明会提升并初始化为 undefined。let 和 const 是块级作用域，不能在同一作用域重复声明；声明会提升，但从块开始到声明语句之间处于暂时性死区（TDZ），访问会抛出 ReferenceError。const 必须在声明时赋值，绑定不能重新赋值，但对象内部属性仍可修改。日常优先 const，需要重新赋值时用 let，新代码通常避免 var。

3. 解构、扩展运算符、剩余参数的用法和场景？ ​

解构按结构提取值并可设置默认值：const { name = '匿名' } = user、const [first, ...rest] = list。扩展运算符把可迭代对象或对象属性展开，常用于复制、合并：const next = [...list, item]、const merged = { ...defaults, ...options }。对象展开是浅拷贝，嵌套对象仍共享引用。剩余参数收集未匹配参数：function sum(...nums: number[]) {}；与扩展不同，剩余参数出现在函数形参或解构左侧。

4. Promise 原理、三种状态、常用方法，如何手写简易 Promise？ ​

Promise 表示一个可能稍后完成的异步操作。状态为 pending、fulfilled、rejected，只能从 pending 转为另外一种，不能逆转。then 注册成功和失败回调并返回新的 Promise，从而串联异步流程；常用方法有 Promise.resolve/reject、all、allSettled、race、any。原生 Promise 还处理 thenable、异常传播和微任务调度，手写版本需要遵循 Promise/A+ 规范，不能简单等同于下面的简化状态机：

js
class TinyPromise {
  state = 'pending'
  value
  handlers = []

  constructor(executor) {
    const resolve = value => this.settle('fulfilled', value)
    const reject = reason => this.settle('rejected', reason)
    try { executor(resolve, reject) } catch (error) { reject(error) }
  }

  settle(state, value) {
    if (this.state !== 'pending') return
    this.state = state
    this.value = value
    queueMicrotask(() => this.handlers.splice(0).forEach(run => run()))
  }

  then(onFulfilled, onRejected) {
    return new TinyPromise((resolve, reject) => {
      const run = () => {
        const callback = this.state === 'fulfilled' ? onFulfilled : onRejected
        if (typeof callback !== 'function') {
          (this.state === 'fulfilled' ? resolve : reject)(this.value)
          return
        }
        try { resolve(callback(this.value)) } catch (error) { reject(error) }
      }
      if (this.state === 'pending') this.handlers.push(run)
      else queueMicrotask(run)
    })
  }

  catch(onRejected) { return this.then(undefined, onRejected) }
}

这是用于说明状态、链式调用和异常处理的教学版本，省略了 thenable 同化、返回自身检测等规范细节，生产代码应使用原生 Promise。

5. async/await 原理、错误捕获、串行与并行？ ​

async 函数总是返回 Promise；await 等待 Promise 的结果，并把后续代码安排在异步续体中执行，不会阻塞整个线程。它可以理解为 Promise 链的语法糖。用 try/catch 捕获 await 的拒绝：

js
try {
  const data = await loadData()
} catch (error) {
  handleError(error)
}

有依赖的任务逐个 await，即串行；互不依赖的任务先发起再 await Promise.all([a(), b()])，即并行。Promise.all 任一失败就拒绝；想收集每个任务的成功或失败结果用 Promise.allSettled。

6. 原型链、原型继承、class 继承？ ​

对象可通过内部原型 [[Prototype]] 连接到另一个对象。访问属性时先查对象自身，再沿原型逐级查找，直到 null，这条链称为原型链。构造函数的 prototype 是实例共享原型的对象，实例的 [[Prototype]] 指向它。ES6 class 是基于原型的语法形式；extends 建立静态和实例原型链，子类构造函数中先调用 super() 才能使用 this。继承适合“是一个”的稳定关系，组合通常更灵活，能减少深层继承耦合。

7. 闭包是什么，有什么用途和风险？如何避免内存泄漏？ ​

函数可以访问其定义时的词法作用域；即使外层函数已返回，只要内层函数仍引用外层变量，这些变量就会被保留，这种函数与其词法环境的组合称为闭包。用途包括封装私有状态、函数工厂、缓存、事件回调。闭包可能延长大对象生命周期；避免无意泄漏的方法是及时移除事件监听器、清理定时器、解除不再需要的引用，不把大型 DOM 或数据长期保存在闭包中。闭包本身不是内存泄漏，无法回收的无用引用才是问题。

8. 手写防抖和节流，适用场景？ ​

防抖是在连续触发时重置计时器，只在停止触发一段时间后执行，适合搜索输入、窗口尺寸稳定后计算。节流限制一段时间内最多执行一次，适合滚动、拖动等高频事件。

js
function debounce(fn, delay = 300) {
  let timer
  return function (...args) {
    clearTimeout(timer)
    timer = setTimeout(() => fn.apply(this, args), delay)
  }
}

function throttle(fn, delay = 300) {
  let last = 0
  return function (...args) {
    const now = Date.now()
    if (now - last >= delay) {
      last = now
      fn.apply(this, args)
    }
  }
}

实际项目还可增加取消、立即执行或尾调用能力；组件卸载时清理尚未触发的定时器。

9. 深拷贝和浅拷贝的实现方式与区别？ ​

浅拷贝只复制第一层，嵌套对象仍共享引用。可用展开语法、Object.assign 或数组展开。深拷贝递归复制嵌套结构，使副本与原对象相互独立。structuredClone(value) 支持多数常见数据类型和循环引用，但不能复制函数、DOM 节点等；JSON 序列化会丢失 undefined、函数、Symbol、特殊对象并且不能处理循环引用。复杂场景应使用符合数据类型需求的库或明确实现拷贝策略。

10. 事件循环中宏任务和微任务的顺序？ ​

JavaScript 执行同步代码；当前调用栈清空后，事件循环会清空微任务队列，再开始下一个宏任务。每个宏任务结束后也会再次清空微任务。常见宏任务有脚本、定时器、I/O、用户事件；常见微任务有 Promise.then/catch/finally、queueMicrotask、MutationObserver。浏览器通常在一次任务及微任务处理后有机会渲染。setTimeout(fn, 0) 仍是后续宏任务，不会立即执行。

11. map、filter、reduce、some、every？ ​

  • map 将每项映射为新数组，长度通常与原数组一致。
  • filter 保留满足条件的项，返回新数组。
  • reduce 将数组归并为单个结果，如求和、分组；应提供初始值以处理空数组。
  • some 判断是否至少有一项满足条件，找到后短路。
  • every 判断是否所有项满足条件，遇到不满足项后短路。

这些方法通常不修改原数组；回调中主动修改对象属性仍会影响对象本身。

12. JavaScript 数据类型、判断方法，null 与 undefined？ ​

原始类型有 undefined、null、boolean、number、bigint、string、symbol；对象类型包括普通对象、数组、函数等。typeof 适合判断大多数原始类型和函数，但 typeof null 是历史遗留结果 "object"，数组也为 "object"。可用 Array.isArray 判数组，用 instanceof 判断原型链关系，用 Object.prototype.toString.call(value) 辅助识别内置类型。undefined 常表示尚未赋值或缺少值；null 通常表示明确设置为空。

13. 如何区分数组和普通对象？ ​

用 Array.isArray(value) 识别数组，它可以正确处理跨 iframe 的数组；普通对象可判断 value !== null && typeof value === 'object' && !Array.isArray(value)，但这也会包含 Date、Map 等对象。若确实要判断普通对象，可结合原型：Object.getPrototypeOf(value) === Object.prototype || Object.getPrototypeOf(value) === null。

TypeScript 高频 ​

1. TS 相比 JS 的优势，项目为什么使用 TS？ ​

TypeScript 在编译期提供静态类型检查、编辑器补全、重构支持和接口契约，能较早发现参数、返回值和数据结构错误。团队项目中有助于跨模块协作和维护。它最终编译成 JavaScript，类型在运行时会被擦除，因此不能替代运行时数据校验；外部接口数据仍应校验。

2. 联合、交叉、interface 和 type？ ​

联合类型 A | B 表示值可以是多种类型之一，使用前通常要缩小类型；交叉类型 A & B 表示同时具备多种类型成员。interface 适合描述对象契约，支持声明合并和 extends；type 可给任意类型起别名，支持联合、映射、条件类型等。两者都能描述对象，按团队约定选用即可。

3. 泛型的作用和使用场景？ ​

泛型把具体类型作为参数传入，在复用逻辑的同时保留输入输出的类型关系。例如 function identity<T>(value: T): T { return value }。常用于 API 响应封装、通用表格、缓存、工具函数和集合类型。必要时可用 T extends SomeType 添加约束，避免泛型退化成 any。

4. 可选属性、只读属性和类型断言？ ​

name?: string 表示属性可缺省；readonly id: number 表示该属性初始化后不能通过该类型重新赋值。类型断言 value as HTMLInputElement 是告诉编译器开发者已确认类型，不会在运行时检查或转换值。断言应有可靠依据，不能用来掩盖不确定数据；外部输入应做运行时校验。

5. Vue 3 + TS 实战写法，如何约束 props？ ​

<script setup lang="ts"> 中可用 defineProps 声明属性类型，必要属性写为非可选，可选属性用 ?，默认值可通过 withDefaults 设置：

vue
<script setup lang="ts">
interface Props {
  title: string
  count?: number
}
const props = withDefaults(defineProps<Props>(), { count: 0 })
const emit = defineEmits<{ (event: 'save', id: number): void }>()
</script>

复杂表单、接口返回值还应定义明确类型；从服务器收到的数据需要运行时校验，TS 类型不会验证 JSON。

6. enum 的使用场景？ ​

枚举用于给一组固定选项命名，例如订单状态。但数字枚举可能产生双向映射，运行时代码也会增加；字符串枚举较直观。很多场景用 as const 对象加联合类型更轻量：const Status = { Ready: 'ready', Done: 'done' } as const，类型为 typeof Status[keyof typeof Status]。选型看是否需要枚举运行时对象和团队约定。

HTML + CSS ​

1. 两种盒模型及全局统一配置？ ​

标准盒模型 content-box 中，声明的 width 只包含内容区；border-box 中，width 包含内容、内边距和边框，更容易计算布局。通常全局设置：

css
*, *::before, *::after { box-sizing: border-box; }

2. 五种定位属性区别、场景和“子绝父相”？ ​

static 是默认文档流定位；relative 保留原位置并可相对自身偏移；absolute 脱离普通文档流，参照最近的非 static 祖先；fixed 通常相对视口固定；sticky 在滚动到阈值前像相对定位，达到阈值后吸附。子绝父相是让父元素 position: relative 建立定位参照，子元素 position: absolute 定位到父容器内，适合角标、覆盖层等。

3. Flex 常用属性和快速居中？ ​

容器常用 display: flex、flex-direction、justify-content（主轴）、align-items（交叉轴）、flex-wrap、gap；子项常用 flex、align-self、order。水平垂直居中：

css
.parent { display: flex; justify-content: center; align-items: center; }

4. Grid 的场景和 Flex 的区别？ ​

Flex 主要处理单一方向的一维排列，适合导航、工具栏、行内对齐；Grid 同时定义行和列，适合整体二维页面布局、卡片网格。两者可以组合使用，不必互相替代。

5. 垂直居中的常见方案？ ​

  • Flex：父元素 display:flex; align-items:center；横纵居中再加 justify-content:center。
  • Grid：父元素 display:grid; place-items:center。
  • 绝对定位加变换：子元素 position:absolute; top:50%; transform:translateY(-50%)。
  • 已知高度时绝对定位配合负 margin-top。
  • 单行文本可用合适的 line-height，但不适合多行或动态高度。
  • 表格布局可用 display:table-cell; vertical-align:middle，旧项目中可能见到。

优先选 Flex 或 Grid，语义清晰且不依赖固定高度。

6. BFC 是什么、怎么触发、解决什么问题？ ​

BFC（块级格式化上下文）是独立的布局区域，内部布局不会随意影响外部。常见触发方式包括根元素、float 非 none、position:absolute/fixed、display:inline-block/table-cell/flow-root、overflow 非 visible。常用于包含浮动子元素、防止外边距与外部折叠、隔离浮动影响。现代写法可用 display: flow-root 创建 BFC，避免用 overflow:hidden 时意外裁剪内容。

7. 清除浮动的方法？ ​

优先用 Flex/Grid 代替不必要的浮动。已有浮动布局时，可在父元素使用 display: flow-root，或经典 clearfix 伪元素：::after { content:""; display:block; clear:both; }。给父元素固定高度不够灵活；单独添加空标签也可清除但会增加无意义标记。

8. 外边距塌陷原因和处理？ ​

相邻块级元素的垂直外边距可能合并；父子之间也可能发生垂直 margin 折叠。它只发生在特定块格式化布局中。可通过父元素建立 BFC（如 display:flow-root）、改用 padding/border、Flex/Grid 布局或调整 DOM 结构避免。不要用随意增加像素的方式掩盖布局关系问题。

9. 响应式布局和媒体查询？ ​

响应式布局让页面根据视口和设备能力调整。常用弹性容器、相对单位、图片自适应、CSS Grid/Flex 和媒体查询：

css
.cards { display: grid; grid-template-columns: repeat(3, 1fr); gap: 16px; }
@media (max-width: 768px) {
  .cards { grid-template-columns: 1fr; }
}

断点应根据内容何时无法良好排布来选，而不是只对应特定设备型号。

10. 移动端适配：rem、vw 和 Vite 插件？ ​

rem 以根元素字号为基准，常通过动态设置 html 字号实现等比缩放；vw 是视口宽度的百分比，适合流式尺寸，通常配合 clamp() 限制上下限。Vite 插件可自动转换设计稿像素到 rem 或 vw，需要统一设计稿宽度、转换规则和忽略项。移动端还需设置 viewport meta、处理安全区、触控尺寸和字体可读性，不宜只做机械换算。

11. 回流和重绘区别，如何减少？ ​

回流（布局）是元素几何尺寸或位置改变后重新计算布局，通常也会导致重绘；重绘是外观变化但布局不变，如颜色变化。减少方式：合并 DOM/CSS 修改、避免读写布局属性交替造成强制同步布局、动画优先使用 transform 和 opacity、减少复杂选择器和大范围布局影响、长列表使用虚拟化。不要无差别给所有元素添加 will-change。

12. Less/Sass 使用经验如何回答？ ​

Less/Sass 提供变量、嵌套、混入、函数等能力，适合复用主题变量和抽取重复样式。回答项目经验时可说明用过的变量体系、组件样式组织、主题或响应式 mixin，以及编译集成方式。嵌套不宜过深，避免选择器耦合；新项目也可结合 CSS 自定义属性、CSS Modules 或原生 CSS 特性选择方案。

二、Vue 全家桶核心 ​

Vue 2 / Vue 3 ​

1. Vue 2 和 Vue 3 的主要区别，如何选型？ ​

Vue 2 主要用 Object.defineProperty 劫持已有属性；Vue 3 基于 Proxy，可拦截属性新增、删除和数组索引等操作。Vue 3 重写了响应式和渲染器，支持组合式 API、Fragments、Teleport、Suspense 等能力，TypeScript 支持也更好。新项目通常选 Vue 3；既有 Vue 2 系统要结合维护周期、生态依赖、升级成本和团队熟悉度评估，不应只因版本新就整体迁移。

2. Vue 响应式原理和 Vue 2 缺陷？ ​

Vue 2 初始化时递归遍历数据属性，用 getter 收集依赖、setter 通知 watcher 更新。它对初始化时不存在的属性和数组下标修改无法直接侦测，需使用 Vue.set、$set 或数组变更方法；深层对象还需递归处理。Vue 3 的 Proxy 代理整个对象，可拦截 get/set/deleteProperty/ownKeys 等操作，覆盖属性增删和数组索引；代价是代理对象与原对象不同，且仍要遵守响应式引用使用规则。

3. 响应式失效场景和解决方案？ ​

  • 解构 reactive 属性得到普通值，断开代理追踪：用 toRef/toRefs，或直接访问 state.x。
  • 用 ref 时漏写 .value（模板顶层会自动解包，JS 中不会）：检查上下文并保持一致。
  • 将整个 reactive 变量重新赋值：通常保留对象并更新属性，或改用 ref 包装对象。
  • 修改数组/对象的非响应式副本、props 或原始对象：确认修改的是代理且不直接改只读 props。
  • watcher 没有读取依赖、异步回调引用了旧值：检查依赖、使用 watch 的显式源或 watchEffect，清理过期请求。
  • 组合式函数返回响应式对象后直接解构：返回 toRefs 或由调用方保留对象引用。

4. computed 与 watch 的区别和场景？ ​

computed 根据响应式依赖计算派生值，默认缓存，适合模板展示或其他计算；应保持纯计算。watch 观察指定数据源，适合发生变化时执行副作用，如请求、写本地存储或与第三方库同步；可配置 immediate、deep、flush。若副作用的依赖自动收集且逻辑简单，可用 watchEffect。

5. v-if 和 v-for 优先级、优化写法？ ​

Vue 3 中同一节点上 v-if 优先级高于 v-for，因此 v-if 不能访问该节点 v-for 声明的变量；Vue 2 的优先级相反，版本差异是常见坑。要筛选列表，使用计算属性先过滤再遍历；要控制整组显示，把 v-if 放到外层 <template>。列表提供稳定且唯一的 key，避免用索引作为会排序或增删列表的 key。

6. 组件 data 为什么是函数？ ​

组件定义可被多个实例复用。若 data 是同一个对象，实例会共享状态；返回对象的函数可为每个实例创建独立数据。Vue 3 Composition API 中通常在 setup 内创建每次调用独有的状态，也遵循这个隔离目的。

7. Vue 组件通信方式有哪些？ ​

常见方式包括：父传子 props；子传父 emit；父组件通过模板引用调用子组件暴露的方法；插槽传递布局和内容；跨层级 provide/inject；共享状态用 Pinia/Vuex；路由参数或 query 传导航状态；事件总线可用于少量松耦合事件（Vue 3 无内置 $on/$off，需额外库）。选择时优先明确单向数据流，避免多套通信方式造成状态来源不清。

8. 父子组件生命周期执行顺序？ ​

首次挂载通常是父 beforeCreate、created、beforeMount，然后子组件对应初始化并执行 beforeMount、mounted，最后父 mounted。卸载时父 beforeUnmount 先执行，子组件先完成 beforeUnmount 和卸载，随后父 unmounted。Vue 2 的钩子名分别是 beforeDestroy/destroyed。异步组件、Suspense 和条件渲染会影响具体时机。

9. 自定义指令和业务场景？ ​

自定义指令适合直接操作 DOM 的可复用行为，例如自动聚焦、权限控制下的元素移除、点击外部关闭、拖拽。Vue 3 可在 mounted/updated/unmounted 等钩子中绑定和清理行为；若逻辑涉及大量状态、模板和生命周期，应该封装为组件或组合式函数，而不是塞进指令。绑定事件时必须在卸载时移除监听。

10. 过滤器、Mixin 的优缺点，现在还用吗？ ​

Vue 2 过滤器只用于模板文本格式化，Vue 3 已移除，建议用计算属性或格式化函数。Mixin 可复用逻辑，但命名冲突、来源不清、隐式合并会增加维护成本；Vue 3 通常优先组合式函数，Vue 2 可用组合式 API 插件或清晰的工具函数。存量项目仍可能使用 mixin，应逐步迁移而不是为了新写法冒险大改。

11. 组合式 API 和选项式 API 对比？ ​

选项式 API 按 data/methods/computed 等选项组织，初学者易理解，适合简单组件；复杂组件的同一业务逻辑分散在多个选项。组合式 API 按功能逻辑组织，可用组合式函数复用，TS 推导和大型逻辑拆分更自然；缺点是需要建立组织规范，避免 setup 变成长函数。两种 API 可按项目和组件复杂度选择。

12. <script setup> 的细节和注意点？ ​

它是单文件组件中 setup() 的编译时语法糖，顶层声明可直接用于模板；defineProps/defineEmits/defineExpose 是编译器宏，不需要导入。宏参数需要可静态分析，不能依赖普通运行时局部变量；子组件默认不向父组件暴露内部成员，需要 defineExpose。顶层 await 会变成异步 setup，应了解其与 Suspense 的关系。对外复用逻辑宜抽成组合式函数。

13. ref、reactive、toRef、toRefs？ ​

ref 可包装基本类型或对象，通过 .value 访问，适合作为单个可替换状态；reactive 代理对象，适合一组结构化状态。toRef(obj, 'x') 创建与对象某属性同步的 ref；toRefs(obj) 为对象的可枚举属性创建 refs，常用于解构返回值并保留响应性。模板会自动解包顶层 ref，JS 中不会；不要把 reactive 属性直接解构成普通变量。

14. Vue 3 组合式生命周期写法？ ​

在 setup 中注册 onMounted、onUpdated、onUnmounted、onBeforeMount、onBeforeUpdate、onBeforeUnmount、onErrorCaptured 等钩子，需在 setup 同步执行阶段注册。onMounted 适合访问已挂载 DOM、启动定时器或第三方库；卸载时在 onUnmounted 清理定时器、事件和订阅。setup 本身替代了 Vue 2 的 beforeCreate/created 主要逻辑。

Vue Router ​

1. hash 和 history 模式原理、区别和部署差异？ ​

hash 模式把路由放在 URL 的 # 后，片段变化不会向服务器发请求，兼容性好，但 URL 有井号。history 模式使用 History API 修改路径，URL 更简洁；直接刷新深层路径时服务器必须回退到 SPA 的 index.html，否则会 404。部署还要正确配置应用 base、静态资源路径和后端 API，避免把接口错误回退到首页。

2. 路由守卫分类？ ​

全局守卫包括 beforeEach、beforeResolve、afterEach；路由独享守卫为路由配置里的 beforeEnter；组件内守卫 Vue 3 Composition API 常用 onBeforeRouteLeave 和 onBeforeRouteUpdate。守卫可返回 false 取消导航、返回路由地址重定向，也可等待异步鉴权。避免多处重复请求权限数据，并确保错误和无限重定向能被处理。

3. 权限路由和动态路由如何实现？ ​

登录后从服务端获取用户角色/权限，前端根据权限映射可访问路由，使用 router.addRoute 动态添加；导航守卫检查登录状态和目标权限，无权限重定向到 403 或默认页。刷新页面时重新加载用户信息并注册路由，再继续导航。隐藏菜单只是体验层控制，后端仍必须校验接口权限；登出或切换账号时清理动态路由和权限状态。

4. 路由懒加载和优化？ ​

路由组件用动态导入：component: () => import('./views/Report.vue')，构建工具据此拆分代码，进入页面时再加载。可结合路由分组、预加载常用页面、加载状态和错误重试优化体验；避免把首屏依赖拆得过碎导致过多请求，也要分析构建产物确认分包有效。

5. 路由传参方式及优缺点？ ​

params 通常配合动态路径，如 /users/:id，适合资源标识；query 出现在 ? 后，可分享和刷新保留，适合筛选条件；state 或内存状态适合临时导航数据，但刷新或直接访问可能丢失。敏感信息不应放 URL；参数需校验和编码，避免把过量业务对象塞入路由。

6. 重复点击路由报错如何处理？ ​

Vue Router 4 的重复导航通常通过 router.push 的 Promise 结果处理；先确认它确实是重复导航，再在调用层忽略对应情况或封装导航函数。Vue Router 3 曾常见 NavigationDuplicated 拒绝，可检查错误类型后处理。不要简单吞掉所有导航错误，否则守卫异常或真实路由错误会被隐藏。按钮也可在当前路由时禁用。

状态管理 ​

1. Vuex 五大核心和流程？ ​

Vuex 典型核心为 state（状态）、getters（派生状态）、mutations（同步修改状态）、actions（可异步业务逻辑并提交 mutation）、modules（模块拆分）。组件读取 state/getters，通过 dispatch 调 action，action 调接口后 commit mutation 更新状态。Vuex 4 仍用于 Vue 3 存量项目，新项目常评估 Pinia。

2. Vuex 模块化如何拆分？ ​

按业务域拆模块，例如用户、权限、购物车、配置；模块内集中定义状态、派生值和操作。命名空间可减少 action/mutation 名冲突；模块间少互相直接访问，跨模块业务由组合 action 或服务层协调。只把跨页面共享、生命周期较长的状态放全局，临时 UI 状态留在组件，避免 store 变成所有数据的垃圾桶。

3. Pinia 相比 Vuex 的优势，为什么替换？ ​

Pinia API 更轻，默认没有 mutations，直接在 action 中更新状态；模块无需复杂嵌套命名空间，TS 类型推导和开发体验较自然，也支持插件。是否替换要考虑团队迁移成本、现有生态和项目维护周期。小型新项目可直接选择 Pinia；存量 Vuex 若稳定，通常按业务模块逐步迁移。

4. 全局状态管理与持久化最佳实践？ ​

只存真正跨页面共享的状态；区分服务端数据、会话态和临时 UI 状态。按业务域拆 store，提供清晰 action，并定义初始化、登出清理和异常恢复。持久化只存必要字段：主题、非敏感偏好可用 localStorage；短期会话可考虑 sessionStorage。不要把 access token 等敏感凭据随意存储；需评估 XSS 风险、版本迁移、过期和多标签页同步。大型服务端数据通常还应考虑缓存策略而非无限持久化。

通用组件封装 ​

1. 如何封装 Vue 3 + TS + Element Plus 通用弹窗？ ​

用受控的 modelValue 控制显示，defineEmits 发出 update:modelValue；通过 props 配置标题、宽度、是否显示底部按钮等，通过具名插槽提供内容和 footer。确认按钮触发明确事件，异步提交时暴露 loading 状态；关闭时按需求清理表单。类型要清楚，避免组件内部强耦合具体业务接口。Element Plus 的 el-dialog 已处理遮罩和键盘行为，封装层应增加团队统一约定而不是重复造基础功能。

2. 业务组件封装思路和原则？ ​

先识别稳定、重复的业务交互，再定义输入（props）、输出（events）和插槽扩展点；内部状态尽量局部化，副作用与 API 请求边界清晰。保证单一职责、默认值合理、错误状态可观察，并覆盖空态、加载态、权限和键盘可访问性。先在多个真实页面验证，再抽象公共能力，避免过早设计成万能组件。

3. 高内聚低耦合、props 规范和插槽？ ​

高内聚表示组件围绕单一职责组织；低耦合表示组件不依赖调用方的内部实现。props 应命名明确、类型和默认值完整、只读使用；子组件通过事件向父级报告变化，不直接修改 props。默认插槽适合主体内容，具名插槽适合 header/footer 等结构扩展，作用域插槽用于向调用方提供渲染所需的数据。

4. 如何设计可配置通用组件？ ​

区分稳定通用项和业务特例：通用外观行为用 props 配置，内容结构用 slots，用户操作用 events，复杂渲染用 render/插槽扩展。配置应有默认值和 TS 类型，避免十几个互相影响的布尔参数；遇到复杂差异可用明确的变体类型或组合子组件。保持向后兼容，并记录使用示例和限制。

5. 团队公共组件库怎么搭建？ ​

统一仓库或 monorepo 管理组件、样式、类型和文档；确定 Vue/Element Plus 等 peerDependencies、构建 ESM/CJS 或团队目标格式、按需导出和样式入口。建立命名、版本、变更日志、发布和兼容策略，使用组件文档展示 API 与示例，配合类型检查、单元/视觉验证和 CI。先沉淀真实复用组件，再制定贡献流程，维护者明确。

三、SPA 大型单页应用架构 ​

1. 大型 SPA 目录结构如何设计？ ​

按职责和业务域结合组织，常见结构包括 app（入口、路由、全局插件）、pages/views（页面）、components（通用组件）、features/modules（业务域）、api/services（接口）、stores（全局状态）、composables（组合式逻辑）、utils、types、assets。规模变大后可按领域模块内聚页面、接口和组件，避免单一大目录。结构应服务团队查找和依赖边界，不追求层级越多越好。

2. 大型项目如何做模块拆分和业务分层？ ​

先按业务领域拆模块，再明确模块对外接口；页面协调流程，业务组件承载交互，服务层负责接口，领域逻辑/组合式函数处理可复用状态和规则，工具层只放无业务副作用的通用函数。限制跨模块直接引用内部文件，公共能力通过明确入口导出。根据真实依赖图迭代拆分，避免为分层而产生大量无意义转发文件。

3. 接口层、工具层、组件层、页面层如何协作？ ​

页面组装组件并控制页面流程；组件展示和响应用户操作；接口层负责请求、参数和响应类型；工具层提供纯函数和基础能力；状态层保存确需共享的数据。依赖方向尽量从页面指向较底层模块，底层不要反向依赖页面。接口错误、加载状态和权限处理保持一致并可观测。

4. 大型 SPA 首屏慢的原因和优化？ ​

先用 Lighthouse/Performance、网络面板和构建分析定位是网络、JS 解析执行、接口等待还是渲染瓶颈。常见措施：路由懒加载和合理分包、移除未使用依赖、压缩并 Brotli/gzip、CDN 与长缓存、关键资源 preload、图片现代格式和尺寸压缩、首屏接口并发与缓存、减少同步初始化、虚拟化长列表、SSR/预渲染适用于 SEO 或首屏关键场景。每次优化用真实指标验证，避免只凭 bundle 大小猜测。

5. SPA 的优缺点？ ​

优点是页面切换无需完整刷新，交互连续、状态可复用，前后端可通过 API 解耦。缺点是首屏 JavaScript 和客户端渲染成本、SEO 与分享预览需要额外处理、路由回退和权限边界要设计、客户端状态复杂度上升。SSR、静态生成、代码分割能改善部分问题，但也增加部署与架构复杂度。

6. 页面权限和按钮权限如何实现？ ​

登录后获得用户角色/权限点，路由层控制页面访问，页面内通过指令或组件封装控制按钮显示/禁用；权限数据由统一 store/服务管理，退出登录清理。前端权限用于界面体验和减少无效操作，不能替代服务端鉴权，所有敏感接口必须由后端校验。对无权限路由提供明确 403 页面并记录异常访问。

7. 全局异常如何统一捕获？ ​

分层处理：请求拦截器处理网络错误、超时和业务码；Vue app.config.errorHandler 捕获组件渲染和事件处理错误；浏览器 error 与 unhandledrejection 监控未捕获异常；关键异步边界使用局部 try/catch 并给用户可恢复提示。日志附带版本、路由、用户匿名标识和 trace id，脱敏后上报；避免重复弹出同一错误，也不吞掉错误导致问题不可见。

8. 接口封装和请求/响应拦截器怎么设计？ ​

统一封装 baseURL、超时、序列化、认证头、取消请求和响应类型；请求拦截器注入认证信息并做公共参数处理，响应拦截器统一处理 HTTP 状态和业务错误。业务 API 按领域单独定义，调用方仍要有清晰类型和错误处理。避免拦截器把所有错误都转成空数据；支持 AbortController 取消过期请求，敏感信息不写日志。

9. 全局常量、枚举、字典如何管理？ ​

代码内稳定常量按领域集中并导出类型（如 as const）；后端动态字典从服务端获取并缓存，明确加载、刷新和失效策略；环境配置使用环境变量且区分公开与服务端秘密。常量要有来源和命名规范，避免一个巨型文件。字典显示值与业务 code 分开，接口仍按 code 交互。

四、前端性能优化 ​

1. 从输入 URL 到页面完整展示经历什么？ ​

浏览器解析 URL，查缓存、DNS 解析并建立 TCP/TLS 连接，发送 HTTP 请求；服务器返回 HTML，浏览器解析 HTML 构建 DOM，下载并解析 CSS 构建 CSSOM，二者合成渲染树，计算布局并绘制、合成。JS 加载执行可能阻塞解析，也可能动态修改 DOM/CSS 并触发后续渲染。图片、字体等子资源并行下载。之后发生交互、异步数据更新和重绘。面试可补充缓存命中、HTTP/2 或 HTTP/3、Service Worker 等分支。

2. 首屏加载优化有哪些？ ​

先定义并测量 LCP、FCP、INP 等指标；控制首屏关键资源体积，拆分非首屏代码、延迟加载路由和非关键组件；压缩图片并提供合适尺寸/现代格式；关键字体和主视觉使用合理 preload；减少阻塞脚本与 CSS；接口并行、缓存稳定数据；SSR/静态生成改善首屏可见内容。需在目标设备和网络复测并检查回归。

3. 网络层优化：CDN、压缩、缓存？ ​

静态资源放 CDN 降低访问延迟；启用 Brotli 或 gzip 压缩文本资源；带内容 hash 的静态文件设置长期 Cache-Control: max-age=31536000, immutable，HTML 使用较短缓存或协商缓存，发布时保证入口能更新到新 hash 文件。API 缓存需按数据一致性、用户隔离和授权谨慎设置。监控 CDN 命中率、传输体积和失败率。

4. 资源优化：图片、懒加载、预加载？ ​

图片按展示尺寸生成，压缩并采用 WebP/AVIF 等支持格式，首屏关键图避免懒加载并可优先加载；非首屏图片使用 loading="lazy"，为图片声明宽高避免布局偏移。preload 用于当前页面确定会用到的关键资源，prefetch 用于可能的后续导航资源；错误预加载会争抢带宽。视频、字体也应控制尺寸和加载时机。

5. 代码优化：分包、懒加载、移除冗余？ ​

路由动态导入，按业务拆分 chunk；分析 bundle 找大依赖，优先按需导入或用小型替代方案；启用 tree shaking 的 ESM 构建，删除不可达代码和重复 polyfill；控制公共 chunk，避免过度拆分产生大量请求。构建后查看依赖分析报告，并在真实网络测量下载、解析和执行成本。

6. 渲染优化：回流重绘和虚拟列表？ ​

减少 DOM 数量、避免布局读写交错、合并批量更新、动画使用 transform/opacity；合理使用虚拟列表减少长列表中实际挂载的节点。避免不必要的深层响应式和昂贵计算，使用分页、缓存或 computed。应以性能面板确认热点，保持语义和可访问性。

7. 虚拟滚动原理和场景？ ​

只渲染可视区域附近的少量列表项，其余由占位容器维持滚动总高度；滚动时根据偏移量计算起始索引，复用或更新可见节点。适用于数千条以上长列表或大表格。固定高度实现简单；动态高度需要测量、缓存高度并修正偏移，复杂度较高。要处理滚动定位、键盘导航、无障碍和数据更新。

8. 浏览器强缓存和协商缓存？ ​

强缓存由 Cache-Control: max-age、s-maxage 等控制，未过期时浏览器直接使用，不请求服务器；Expires 是较旧的绝对时间机制。缓存过期后可用 ETag/If-None-Match 或 Last-Modified/If-Modified-Since 发起条件请求，资源未变返回 304。生产静态资源常用文件 hash + 长期强缓存，HTML 需能发现新版本。

9. 本地存储方式区别与选型？ ​

localStorage 同源持久保存、容量有限且同步阻塞；sessionStorage 按标签页会话保存；Cookie 会随匹配请求发送，可设置 HttpOnly/Secure/SameSite，容量小；IndexedDB 适合大量结构化异步数据；内存状态随页面刷新丢失。根据生命周期、容量、是否需随请求发送和安全要求选择，敏感信息应避免暴露给可被 XSS 读取的存储。

10. 打包体积过大怎么优化？ ​

先用构建分析插件查看 gzip/brotli 后体积和依赖来源；检查重复版本、整包引入、未 tree-shake 的依赖、过大的 locale/icon 等资源；按需导入、动态分包、替换依赖、压缩静态资源；删除不再使用的代码。也要看 JS parse/execute，不只看压缩包大小。用预算和 CI 体积报告防止回归。

11. 骨架屏和加载动画如何提升体验？ ​

骨架屏用页面结构占位，让用户尽早看到布局，适用于等待时间较长且页面结构可预测的场景；短操作使用按钮 loading 或局部占位。加载状态要有超时、失败和重试反馈，避免无限转圈；尽可能保留已显示内容，降低布局偏移。骨架屏不能替代真实性能优化。

12. 前端性能和异常监控？ ​

采集 Web Vitals（LCP、INP、CLS 等）、资源加载耗时、路由切换、API 延迟和错误；通过 PerformanceObserver、错误事件和请求封装采集，关联版本、设备、网络和路由维度并脱敏。采样控制成本，设置阈值和告警，结合用户会话回放或 sourcemap 定位源码。关注真实用户分布，不只看本机 Lighthouse 分数。

五、前端工程化 ​

1. Webpack 和 Vite 原理区别，如何选型？ ​

Webpack 开发时通常先构建依赖图并打包模块，再提供开发服务；Vite 开发环境利用浏览器原生 ESM 按需提供源码，并预构建依赖，生产构建通常交给 Rollup（具体版本也可能采用新打包器）。Vite 冷启动和局部更新通常更快，Webpack 生态和复杂定制历史积累丰富。选型看项目生态、插件、构建需求和团队迁移成本。

2. 为什么 Vite 开发阶段通常更快？ ​

传统打包器需要先处理较大模块图才能启动；Vite 开发服务器按浏览器请求提供 ESM，修改文件时只更新相关模块，减少全量重打包。第三方依赖通过预构建减少请求和兼容问题。生产构建仍需打包优化，因此“开发快”不等于生产包必然更小或构建永远更快。

3. Webpack 常用配置：入口、出口、loader、plugin？ ​

entry 指定入口，output 设置产物路径和文件名；module.rules 用 loader 转换资源（如 Babel、CSS、图片）；plugins 扩展构建流程（如 HTML 生成、环境变量、压缩）；resolve 配置别名和扩展名；mode 设置开发/生产优化。loader 通常处理单个模块，plugin 可参与更广泛的构建生命周期。

4. Babel 的作用和兼容性处理？ ​

Babel 将新语法转换为目标浏览器可理解的语法；@babel/preset-env 根据 Browserslist 目标选择转换，必要时注入 polyfill。语法转换不等于 API 补齐，需确认 polyfill 策略，避免重复或过量注入。兼容性应由目标浏览器数据、测试矩阵和错误监控确定，而非无目标地转换所有代码。

5. 前端跨域解决方案？ ​

浏览器同源策略限制跨源脚本读取响应，开发环境可用 Vite/Webpack dev server 代理；生产可由 Nginx/BFF 反向代理；服务端配置 CORS 响应头，允许明确来源、方法和请求头，带凭证时不能把 Access-Control-Allow-Origin 设为 *。JSONP 仅适用于 GET 且已过时。跨域是浏览器安全策略问题，前端不能单独绕过；CORS 也不是认证授权机制。

6. 如何区分开发、测试、生产环境？ ​

使用 .env.development/.env.production 等环境文件与构建模式区分 URL、开关和公开配置；只把允许暴露给浏览器的变量放入前端构建，任何前端环境变量最终可被用户查看，不能放密钥。CI/CD 注入环境配置，避免手改产物；测试环境与生产保持尽量一致并验证 API 域名、日志级别和 sourcemap 策略。

7. Git 工作流、协作规范和分支管理？ ​

采用 trunk-based 或 Git Flow 等一种团队共识：从主干开短期功能/修复分支，提交遵循清晰 message，提交前检查和自测，通过 PR/MR review 与 CI 后合并，发布用 tag/版本记录。保护主分支、避免多人长期共用同一功能分支，及时同步并解决冲突。流程轻重应匹配团队规模和发布频率。

8. ESLint + Prettier 如何落地？ ​

ESLint 检查代码质量和潜在错误，Prettier 统一格式；配置好后接入编辑器、提交钩子和 CI。避免两个工具对格式规则互相覆盖，通常由 Prettier 负责排版，ESLint 负责代码规则。渐进式处理历史问题，新增代码先达标，再制定修复旧文件的计划；CI 阻止违规变更进入主干。

9. 前端自动化部署流程？ ​

代码合并触发 CI：安装锁定依赖、静态检查、测试、构建并产出制品；将制品部署到测试环境，执行冒烟或验收；审批或满足发布策略后发布到生产，配合 CDN 缓存刷新、版本记录和健康检查。使用可回滚版本、环境隔离和安全凭据管理。部署成功还要验证真实服务，而不只看流水线绿色。

10. 工程化怎样提升团队效率？ ​

通过脚手架和统一依赖减少重复搭建；代码规范、类型、组件库和文档降低协作成本；CI 自动执行检查和部署；模块边界和 API 契约减少集成冲突；监控与可回滚发布缩短故障恢复。衡量成效可看从提交到发布的周期、缺陷率、构建耗时和重复工作量，避免引入没人维护的工具链。

11. 如何优化构建速度？ ​

先定位耗时在依赖安装、类型检查、loader、压缩还是打包；启用缓存和增量构建，减少不必要插件与重复转换，缩小扫描范围，升级或替换慢插件，合理并行处理；将类型检查与打包并行需保证 CI 最终都检查。优化后比较冷/热构建数据并确保产物一致。

六、微前端架构 ​

1. 微前端是什么，解决什么痛点？ ​

微前端把大型前端按业务或团队拆成可独立开发、构建、发布的子应用，由主应用在运行时组合。它解决多团队并行、技术栈渐进迁移和独立发布等问题，但会增加路由、通信、依赖、样式、性能和运维复杂度。若单体 SPA 仍可由一个团队高效维护，通常不必引入微前端。

2. qiankun、micro-app、iframe 的优缺点？ ​

qiankun 基于 single-spa，提供应用注册、生命周期、样式隔离和 JS 沙箱能力，生态成熟但需要适配构建和路由。micro-app 提供 Web Component 风格接入和隔离能力，上手相对直接，需评估版本和具体隔离配置。iframe 隔离强、接入遗留系统直接，但通信、尺寸、路由、体验和资源共享较麻烦。最终按隔离要求、独立部署和现有系统兼容性选型。

3. qiankun 基座和子应用搭建流程？ ​

基座注册子应用的名称、入口、激活路由和挂载容器，设置主子应用生命周期并启动；子应用导出 bootstrap/mount/unmount 等生命周期，开发环境支持独立运行，生产构建配置可被基座加载的资源（常见为 UMD）并处理跨域响应头。统一路由 base、公共依赖、样式和鉴权约定，再按路由激活子应用。具体构建配置随 Vite/Webpack 插件和 qiankun 版本而不同。

4. 子应用间通信方案？ ​

优先由基座提供受控的全局状态/事件接口，或通过 URL 路由和 query 传可分享状态；共享后端作为权威数据源，子应用通过 API 协作。通信协议需有类型、版本和生命周期清理。避免多个子应用直接互相调用内部 store，形成隐式依赖。

5. 样式隔离和 JS 沙箱如何实现？ ​

样式隔离可用 CSS Modules、命名空间、Shadow DOM 或框架提供的 scoped 样式；动态样式和全局样式仍需检查。JS 隔离由框架对 window 等全局对象做代理或快照，限制子应用污染主应用；这不是强安全边界，不能运行不可信代码。仍要规范全局事件、定时器、全局变量和第三方脚本清理。

6. 微前端落地常见问题？ ​

常见问题有子应用静态资源路径错误、跨域、路由 base 不一致、全局 CSS 冲突、重复框架依赖、主子应用通信耦合、卸载后事件未清理、首屏多应用加载变慢。通过独立运行和集成两套测试、统一接入契约、资源部署规范、版本兼容策略、性能监控和回滚解决。面试时结合真实问题说明定位过程，不要只罗列框架功能。

7. 什么场景适合微前端？ ​

适合多个团队独立交付不同业务域、应用体量大且需要渐进迁移，或已有异构系统需统一入口的场景。若项目小、团队少、共享 UI 与状态很多，微前端可能增加不必要的集成成本。决策前比较模块化单体、monorepo 和微前端的维护成本。

七、项目实战与业务问答 ​

1. 独立负责过哪些复杂模块？ ​

用真实项目按“背景—目标—约束—方案—实施—结果—复盘”回答：说明用户和业务量、自己负责的边界、关键技术决策、遇到的问题和量化结果。示例模板：“我负责【模块】，主要解决【问题】；我先拆成【页面/接口/状态】，采用【方案】处理【难点】，通过【指标或交付结果】验证，后续还改进了【复盘】。”不要虚构指标或把团队成果说成个人独立完成。

2. 拿到产品需求后的开发流程？ ​

澄清目标用户、边界条件、验收标准和异常流程；评估接口、权限、兼容性及风险；拆任务并与设计/后端对齐；设计数据流和组件边界；开发中保持小步提交；自测正常、边界和异常场景；联调、代码评审、灰度/发布；上线后看监控和反馈，补充文档与复盘。

3. 如何保障代码和交付质量？ ​

需求评审和验收标准前置，使用类型约束、Lint、代码评审、自动化构建和测试；针对关键流程做单元、组件或端到端验证；自测不同权限、空数据、失败、慢网络和兼容环境；发布使用灰度、监控、回滚预案。质量由流程和可观测性共同保障，不以“我本地跑过”作为唯一证据。

4. 复杂表单如何设计和统一校验？ ​

先按业务步骤和字段组拆分，定义表单数据模型、校验规则和依赖关系；用表单组件管理触发时机、错误提示、动态字段和清理；规则尽量可复用并支持异步校验，避免每个页面各写一套。提交时前端校验改善体验，后端仍校验数据。长表单可分步、草稿保存并处理离开提示，提交过程防重复。

5. 大数据列表如何做性能优化？ ​

采用服务端分页/筛选减少数据传输；表格列和渲染器精简，避免每行创建重型组件；长列表使用虚拟滚动；请求防抖、取消过期请求并缓存合适查询；稳定 key、避免深层响应式和重复计算；大数据导出交给后端异步任务。根据真实数据量和交互需求选择方案，不能只做前端虚拟化忽略接口成本。

6. 最难排查的问题怎么讲？ ​

挑一个真实案例，按“现象和影响—复现条件—假设—采集证据—定位根因—修复—验证—预防”说明。展示如何用日志、浏览器性能面板、网络请求、二分排查或最小复现缩小范围；最后讲指标和防回归手段。强调团队协作和自己负责的部分，避免只讲最终代码。

7. 如何做前端兼容性处理？ ​

先根据用户和产品确定浏览器支持矩阵；用 Browserslist/Babel、CSS 前缀和必要 polyfill 处理语法与 API；对关键功能做特性检测而非 UA 猜测；在真实浏览器或自动化设备矩阵验证布局、输入、下载等流程。兼容方案也要检查 polyfill 体积和安全更新。

8. 移动端和 PC 端开发侧重点？ ​

移动端更关注触控尺寸、滚动手势、安全区、软键盘、网络波动和性能预算；PC 端更关注复杂信息密度、多列布局、键鼠效率和大屏适配。共享业务逻辑和设计 token，针对交互与布局做响应式或独立组件；结合真实设备测试，而非只用桌面缩放模拟。

八、软实力与编程思想 ​

1. 如何理解模块化和组件化？ ​

模块化按代码职责和依赖边界拆分逻辑，组件化将 UI、行为和接口封装成可组合单元。两者都用来控制复杂度和促进复用；抽象应由稳定的重复需求驱动，模块接口清楚，组件职责单一。复用次数不是唯一目标，理解和维护成本更重要。

2. 如何保证可读性和可维护性？ ​

使用有意义的命名、短而聚焦的函数、明确的数据流和错误处理；消除重复但不制造过度抽象；补关键边界注释、类型、测试和使用文档；保持小改动和持续重构。代码读者通常比作者多，优先让意图明显，而不是追求炫技。

3. 日常代码和命名规范？ ​

遵守团队约定并用自动化格式化；变量和函数使用能描述意图的名称，布尔值常用 is/has/can 前缀，事件处理函数用 handle/on 约定；组件名使用 PascalCase，常量是否全大写按团队规范；避免缩写和语义不清的 data/temp。命名要能区分领域含义，如 userId 与 accountId。

4. 如何进行团队技术沉淀？ ​

把重复问题和有效方案整理成可搜索的文档、模板、组件或脚手架；通过技术分享和评审让团队共同维护；指定负责人、更新时间和适用版本，定期清理过期资料。沉淀内容应来自真实问题并提供示例，避免只积累无人使用的长文档。

5. 平时如何学习和跟进技术变化？ ​

围绕项目问题阅读官方文档和变更说明，做小型验证后再决定是否采用；关注浏览器、框架和构建工具的稳定版本与安全公告；通过实践、代码评审和复盘巩固。技术选择看兼容性、维护成本和业务收益，不为了追新而频繁迁移。

九、加分题 ​

1. 同源策略和跨域？ ​

同源要求协议、主机和端口都相同。浏览器同源策略限制脚本读取不同源的响应和访问部分资源，保护用户数据；它不等于禁止所有跨域请求。常见解决方案是服务端 CORS、反向代理、BFF；开发代理只改善本地开发，生产需要真实服务端配置。CORS 预检请求会先用 OPTIONS 协商权限，带凭证时需指定具体来源并设置允许凭证。

2. 本地缓存、会话缓存、持久缓存区别？ ​

若这里指 Web Storage，sessionStorage 按标签页会话保存，关闭标签页通常清除；localStorage 同源持久保存直到主动删除。若指 HTTP 缓存，则要区分内存缓存、磁盘缓存、强缓存和协商缓存。回答时先确认语境。两种 Web Storage 都是同步、容量有限，存敏感信息要谨慎。

3. HTTP 常用方法和状态码？ ​

方法：GET 获取资源，POST 创建或执行操作，PUT 整体替换，PATCH 部分修改，DELETE 删除，HEAD 只取响应头，OPTIONS 查询通信选项。常见状态码：200 成功、201 创建、204 成功无响应体；301/302 重定向，304 使用缓存；400 请求错误、401 未认证、403 无权限、404 未找到、409 冲突、422 语义校验失败、429 限流；500 服务端错误、502 网关错误、503 暂不可用。具体语义还需看接口约定。

4. TCP 三次握手和四次挥手？ ​

三次握手：客户端发 SYN 表示要建立连接；服务端回 SYN+ACK 表示收到并准备好；客户端回 ACK，双方确认收发能力并建立连接。四次挥手通常是：一方发 FIN 表示自己不再发送；另一方 ACK 并可继续发送剩余数据；另一方完成后发 FIN；最初一方 ACK 后进入等待状态，确保最后的 ACK 有机会到达。TCP 是全双工，两个方向可分别关闭，因此通常需要四个报文。

5. XSS、CSRF 攻击和防御？ ​

XSS 是攻击者让恶意脚本在用户浏览器中执行，分存储型、反射型和 DOM 型；通过上下文正确转义、避免不安全 HTML、采用 CSP、审查第三方脚本降低风险。CSRF 借用户已登录凭据诱导浏览器向站点发请求；可用 SameSite Cookie、CSRF token、校验 Origin/Referer、敏感操作二次确认。CORS 不是 CSRF 防护；防护需结合 Cookie、认证方式和请求设计。

6. 接口并发请求怎么处理？ ​

按场景选择：彼此独立且都必须成功用 Promise.all；需要全部结果用 allSettled；只需最快成功用 Promise.any；限制并发数用队列或任务池；防止重复提交用锁或幂等 key；搜索请求用 AbortController 取消旧请求并防止旧响应覆盖新结果。服务端仍需保证写操作幂等和正确性。

7. 长轮询和 WebSocket 场景？ ​

长轮询由客户端发请求，服务端有消息或超时后响应，客户端再立即发起下一次请求，兼容性好但连接和请求开销较高；适合低频实时、基础设施不支持 WebSocket 的场景。WebSocket 建立后提供全双工长连接，适合聊天、协同、行情等频繁双向消息；需处理心跳、重连、鉴权过期、消息顺序和扩缩容。若只是服务端单向推送，也可评估 SSE。
